# AzmoonRep — Spaced-Repetition Learning Platform for Iranian Math Exam Questions

**Version:** 1.0 (draft for review)
**Date:** 2026-11-14
**Status:** Design — awaiting client edits before implementation

---

## 1. Product Overview

A web platform (in Persian language) where students practice math exam questions (grades 9–12, رشته ریاضی و فیزیک).
it is currenly only supports math but latter we add other courses too
Unlike flashcard apps that repeat *words*, this platform repeats *concepts*: after a student
answers a question, the system schedules the **concept** for review, and at review time serves a
**different but equivalent question** — either from the existing question bank or freshly
generated by AI.

**Core loop:**

```
answer question → system learns which concept was weak → schedule concept
→ tomorrow (or later) the concept is "due" → serve a DIFFERENT question
testing the same concept → repeat
```

**Users:** students (primary), admin/content-manager (secondary), system (AI generation worker).

---

## 2. Guiding Principles

1. **Text is data.** Questions are stored as Markdown + LaTeX math (`$...$`), never as flat
   images. Images only for irreducible graphics (geometry figures). This enables any font size,
   any device, search, and AI processing.
2. **Concepts are the unit of mastery**, not questions. All statistics, scheduling, and UI
   progress is computed per concept.
3. **Never repeat the exact question** if an alternative exists. Exact repetition is the last
   resort (single-question families).
4. **AI-generated questions are never trusted blindly.** Every generated question passes an
   independent solver check before a student ever sees it, and is flagged `reviewed=false`
   until a human (or stats) validates it.
5. even those questions that are extracted from PDF files, images, etc, needs manager approval,
so, manager can either approve, delete, or ask for ai refinement with a text,

5. **Explainability.** Every scheduling decision is derivable from stored data; no black boxes.

## 3. Domain Model

### 3.1 Curriculum Tree (static, imported from books_catalog.json)

```
Book (کتاب)  e.g. "حسابان (۱)", پایه یازدهم
 └─ Chapter (فصل)  e.g. "فصل ۴: مشتق"
     └─ Lesson (درس)  e.g. "آهنگ متوسط تغییر و آهنگ لحظه‌ای تغییر"
         └─ Concept (مفهوم / skill node)  e.g. "محاسبه مشتق تابع کسری"
```

- Books/chapters/lessons: imported once from `main books/books_catalog.json` (already extracted).
- Concepts: the finest granularity. One lesson contains 1–8 concepts. Concepts are defined once
  per lesson by an admin/LLM pass, then stable forever (immutable IDs).
- Concepts may have **prerequisite edges** (DAG) within a lesson/chapter, e.g.
  «مشتق تابع کسری» requires «مشتق ضرب و تقسیم». Used to suggest remedial concepts.

### 3.2 Template Family

A **template** is a named reasoning pattern, e.g.
`decimal_repeating_to_fraction_simple` («تبدیل اعشار متناوب ساده به کسر»).
A template belongs to exactly one concept. One concept may have several templates
(e.g. word-problem variant vs. direct-computation variant).

### 3.3 Question (instance)

An actual question, always linked to: one concept + one template + difficulty + answer.

```json
{
  "id": "q_012345",
  "concept_id": "c_hesaban1_f4_moshtaq_kasri",
  "template_id": "t_moshtaq_kasri_direct",
  "grade": 11,
  "book_code": "C112214",
  "chapter": 4, "lesson": 2,
  "type": "multiple_choice_4",          // | tashrihi | gapfill
  "difficulty": 2,                       // 1..5, initially heuristic, later calibrated
  "stem_md": "…متن سؤال با $\\frac{1}{x}$ …",
  "options": ["…", "…", "…", "…"],       // for MCQ; null for tashrihi
  "answer": 2,                           // option index (1-based) or full solution text
  "solution_md": "…حل تشریحی…",
  "figures": ["fig1.png"],               // relative paths
  "source": "bank | ai_generated",
  "reviewed": true,
  "language": "fa"
}
```

Storage per question: a folder or object-storage key
`questions/{grade}/{book}/{concept}/{q_id}/` containing `meta.json`, `question.md`,
`answer.md`, figure files — identical layout to the pilot bank
(`question_bank/grade9/set_theory_numbers_tizline/`), plus a search index row in the DB.

### 3.4 Key relations

```
Book 1──n Chapter 1──n Lesson 1──n Concept 1──n Template 1──n Question
Student 1──n Response n──1 Question
Student 1──n ConceptState n──1 Concept
```

## 4. Data Model (PostgreSQL)

```sql
-- curriculum
CREATE TABLE books (
  id TEXT PRIMARY KEY,                 -- e.g. 'C112214'
  name TEXT NOT NULL,                  -- 'حسابان (۱)'
  grade SMALLINT NOT NULL,             -- 9..12
  reshte TEXT NOT NULL DEFAULT 'ریاضی و فیزیک'
);
CREATE TABLE chapters (
  id TEXT PRIMARY KEY,                 -- 'C112214_ch4'
  book_id TEXT REFERENCES books(id),
  number SMALLINT, title TEXT NOT NULL
);
CREATE TABLE lessons (
  id TEXT PRIMARY KEY,                 -- 'C112214_ch4_l2'
  chapter_id TEXT REFERENCES chapters(id),
  number SMALLINT, title TEXT NOT NULL
);
CREATE TABLE concepts (
  id TEXT PRIMARY KEY,                 -- 'c_hesaban1_f4_l2_003'
  lesson_id TEXT REFERENCES lessons(id),
  title TEXT NOT NULL,                 -- 'محاسبه مشتق تابع کسری'
  order_in_lesson SMALLINT,
  prereq_ids TEXT[] DEFAULT '{}'       -- concept ids (DAG within book)
);

CREATE TABLE templates (
  id TEXT PRIMARY KEY,                 -- 't_moshtaq_kasri_direct'
  concept_id TEXT REFERENCES concepts(id),
  name TEXT NOT NULL,
  gen_prompt TEXT                      -- LLM prompt used to generate variants (nullable)
);

CREATE TABLE questions (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id TEXT UNIQUE NOT NULL,      -- 'q_012345'
  template_id TEXT REFERENCES templates(id),
  concept_id TEXT REFERENCES concepts(id),
  difficulty SMALLINT CHECK (difficulty BETWEEN 1 AND 5),
  type TEXT NOT NULL DEFAULT 'multiple_choice_4',
  stem_md TEXT NOT NULL,
  options JSONB,                       -- null for tashrihi
  answer JSONB NOT NULL,               -- {option: 2} or {text: '...'}
  solution_md TEXT,
  figures TEXT[] DEFAULT '{}',
  storage_path TEXT,                   -- folder with figures
  source TEXT NOT NULL DEFAULT 'bank', -- bank | ai_generated
  reviewed BOOLEAN NOT NULL DEFAULT false,
  times_served BIGINT DEFAULT 0, times_correct BIGINT DEFAULT 0,
  embedding VECTOR(768),               -- for duplicate/near-duplicate detection
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON questions (concept_id, difficulty);
CREATE UNIQUE INDEX ON questions (template_id, stem_md_hash);  -- dedupe guard

CREATE TABLE students (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id TEXT UNIQUE NOT NULL,
  grade SMALLINT,                       -- current grade, drives default book set
  display_name TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE responses (
  id BIGINT GENERATED ALWAYS AS IDENTITY,
  student_id BIGINT REFERENCES students(id),
  question_id BIGINT REFERENCES questions(id),
  concept_id TEXT NOT NULL,
  correct BOOLEAN NOT NULL,
  time_ms INTEGER NOT NULL,
  selected_option SMALLINT,             -- null for tashrihi
  answered_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON responses (student_id, answered_at DESC);

CREATE TABLE concept_state (
  student_id BIGINT REFERENCES students(id),
  concept_id TEXT REFERENCES concepts(id),
  ease REAL NOT NULL DEFAULT 2.5,
  interval_days REAL NOT NULL DEFAULT 0,
  due_date DATE NOT NULL DEFAULT current_date,
  streak SMALLINT NOT NULL DEFAULT 0,
  lapses SMALLINT NOT NULL DEFAULT 0,
  total_answers INTEGER NOT NULL DEFAULT 0,
  total_correct INTEGER NOT NULL DEFAULT 0,
  seen_question_ids BIGINT[] DEFAULT '{}',  -- last N served (e.g. 30)
  mastery_level SMALLINT NOT NULL DEFAULT 0, -- 0=نیاموخته 1=درحال‌یادگیری 2=یادگرفته 3=مسلط
  updated_at TIMESTAMPTZ,
  PRIMARY KEY (student_id, concept_id)
);
CREATE INDEX ON concept_state (student_id, due_date);

CREATE TABLE generated_questions_log (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  template_id TEXT,
  request_json JSONB,
  raw_output TEXT,
  validation_json JSONB,               -- solver check result etc.
  accepted BOOLEAN,
  question_id BIGINT REFERENCES questions(id),
  created_at TIMESTAMPTZ DEFAULT now()
);
```

Question *content* (md files, figures) lives on disk/object storage mirroring the pilot layout;
the DB row points to it via `storage_path`. This keeps the bank portable and lets the existing
pilot folders be imported as-is.

## 5. The Repetition Engine

### 5.1 Concept state update (FSRS-lite / SM-2 variant)

After each response, for the response's concept:

```
if correct and time_ms <= 2 * expected_time:      grade = "good"
elif correct:                                     grade = "hard"
else:                                             grade = "again"

again: streak = 0; lapses += 1; ease = max(1.3, ease - 0.2); interval = 1 day
hard:  streak += 1; ease = max(1.3, ease - 0.05); interval = interval * 1.2 (min 1)
good:  streak += 1; ease = min(3.2, ease + 0.1);
       interval = 1 → 3 → 7 if streak<=3 else interval * ease (cap 180 days)

due_date = today + interval
mastery_level: 3 (مسلط)      if streak >= 3 and interval >= 21
               2 (یادگرفته)  if streak >= 2 and interval >= 7
               1 (درحال‌یادگیری) if total_answers >= 1
               0 (نیاموخته)  otherwise
```

`expected_time` per question = median answer time across all students (cold start: 30s MCQ /
90s tashrihi, per difficulty).

### 5.2 Daily queue generation (runs on request: "شروع امروز")

Input: student, today's date. Output: ordered list of ≤ N slots (default 20).

```
1. due      = concepts with due_date <= today AND mastery_level < 3
              ordered by (due_date asc, lapses desc)
2. weak     = concepts with mastery_level = 1 and answered in last 7 days,
              not already in queue (max 3)          # gentle reinforcement
3. new      = concepts never attempted, ordered by curriculum order,
              prerequisites satisfied; take N_new = ceil(N * 0.2)
4. queue    = overdue(due) + due + weak + new
5. per-concept cap: at most 3 slots per concept (2 review + 1 new)
6. interleave: shuffle but keep overdue items in the first half
```

Empty queue → "امروز مروری نداری" + optional practice mode (free choice of chapter).

### 5.3 Question selection for a queue slot

Given slot's concept `c` and student `s`:

```
1. family = all questions of concept c
2. unseen = family − s.seen_question_ids[c]
3. if unseen non-empty:
     target_difficulty = clamp(current_level(c) + streak_bonus, 1, 5)
     pick nearest-difficulty unseen question, prefer source='bank', reviewed=true
4. elif sibling concepts exist (same lesson, mastery < 2):
     re-point the slot to the sibling concept, go to 1
5. else: enqueue a generation job for template of c (async) and serve
     the least-recently-seen question of c (exact repeat — last resort)
```

Seen-question tracking: `concept_state.seen_question_ids` ring buffer (last 30).

### 5.4 Same-day remediation

If a student answers **again** (wrong), the concept is re-inserted at the END of today's
remaining queue — once per day — served with a *different variant* than the one just failed.

## 6. AI Generation Pipeline (worker)

Trigger: selection step 5.4 (family exhausted) or admin bulk-fill ("this concept has < 5
questions"). Queue-based, idempotent.

```
1. BUILD PROMPT
   system: "You are an Iranian math exam writer. Output JSON."
   user: template.gen_prompt + 2 few-shot examples (real bank questions of this
         template, with solutions) + constraints:
         - difficulty ∈ {student level ±1}
         - MCQ with 4 options, exactly one correct, plausible distractors
         - Persian, RTL, math in LaTeX $...$
         - final JSON: {stem, options[4], answer_index, solution, difficulty}

2. GENERATE   (LLM call #1)

3. INDEPENDENT SOLVE   (LLM call #2, no answer given)
   "Solve this question step by step; give final option index."
   reject if solver_option ≠ generator answer_index

4. SANITY CHECKS (rule-based)
   - options are distinct; answer_index ∈ 1..4
   - LaTeX parses; no placeholder text ("..." in numbers)
   - length/format matches template
   - embedding similarity vs. all questions of concept < 0.90  (dedupe)
   - numeric answer sanity: recompute simple arithmetic where template allows

5. STORE: question(source='ai_generated', reviewed=false) + log row

6. FEEDBACK LOOP: if students' correct-rate on this question deviates > 2σ
   from concept average after ≥ 20 responses → flag for human review,
   auto-hide if clearly broken (correct-rate ≈ 0 or ≈ 100%)
```

Cost control: generation is async (queue slot shows "سؤال جدید در حال آماده‌سازی", serves bank
question meanwhile). Target: ≤ 10% of daily slots.

**Provider abstraction:** one interface `LLMProvider.generate(prompt) -> text` with adapters
(OpenAI-compatible API, local model, etc.). Model choice and keys live in config, never in code.

## 7. Difficulty Calibration

Phase 1 (cold start): difficulty from heuristic rules
(source=konkur official → 3; simple computation → 1–2; multi-step → 4; long tashrihi → 4–5).
Phase 2 (data-driven): after ≥ 20 responses per question,
`empirical_difficulty = 1 + round(4 * correct_rate)` replaces the heuristic
(=5 means almost everyone fails). Calibrated difficulty slowly overrides heuristic.

## 8. Backend Architecture

```
                 ┌────────────┐
  Browser ──────▶│  FastAPI    │────▶ PostgreSQL
  (Next.js)      │  REST API   │────▶ Redis (sessions, rate-limit, queue)
                 └─────┬──────┘
                       │ enqueue
                       ▼
                 ┌────────────┐
                 │ Worker      │  AI generation, embedding, difficulty
                 │ (arq/celery)│  calibration, nightly digest jobs
                 └────────────┘
```

- **Framework:** Python FastAPI + SQLAlchemy + Pydantic + Alembic.
- **Auth:** phone-number + OTP (Iranian market standard), JWT access/refresh.
- **Admin:** same API, role-gated (`student`, `admin`); admin UI is a small internal Next.js
  section, not a separate app.

### REST API (v1 sketch)

```
POST /auth/request-otp {phone}
POST /auth/verify-otp {phone, code} -> tokens
GET  /me                             -> profile, grade, today's stats
GET  /curriculum                     -> book/chapter/lesson tree (+ mastery overlay)
POST /sessions/daily                 -> generate & return today's queue
GET  /slots/{slot_id}/question       -> render-ready question (md + figure URLs)
POST /slots/{slot_id}/answer {selected_option | text, time_ms}
     -> {correct, correct_option, solution_md, next_due: "3 روز بعد"}
GET  /progress                       -> per-concept/chapter/book mastery
POST /practice/start {chapter_id, count}   -> free practice (no scheduling side-effects?  see §11.4)
GET  /admin/questions?concept_id=…   -> content management
POST /admin/generate {template_id, count}  -> bulk generation
GET  /admin/stats                    -> per-question/per-concept response stats
```

### Serving questions to the frontend

`GET /slots/{id}/question` returns:

```json
{
  "question_md": "…$\\frac{1}{2}$…",
  "figures": ["https://cdn/.../fig1.png"],
  "options_md": ["…", "…", "…", "…"],
  "type": "multiple_choice_4",
  "time_limit": null
}
```

Answer checking happens server-side; correct answer is revealed only after submission.

## 9. Frontend (Next.js + Tailwind, RTL-first)

### 9.0 UI philosophy — the exam candidate

These users are **preparing for a real exam**. They are not casual scrollers. Three principles
drive every screen:

1. **Zero ambiguity at start of day.** The student must know — *before* pressing anything —
   exactly what today's session contains: how many questions, which concepts, how long it will
   take. Nothing is a surprise. Uncertainty ("what will they ask me?") is anxiety, and anxiety
   kills concentration.
2. **One thing on screen.** During a session there is no menu, no sidebar, no browsing, no
   other questions visible. The screen shows exactly one question and nothing else. Navigation
   happens only between sessions, never inside one.
3. **The plan rules the app.** The daily queue is not a random pile — it is derived from the
   student's **study plan** (exam date + their grade's books). The student can always see the
   plan, today's position in it, and what comes tomorrow.

### 9.1 Post-login landing: «برنامه امروز» (Today's Plan)

card** that reads like a work order:


What the student sees on landing:

- **Exact counts and time estimate** (count × median time per question type).
- **Concept names — not question content.** The student knows *what will be asked*
  (which concepts) but not the exact questions (which would defeat testing). This is the
  sweet spot: predictability without voiding the test.
- **Yesterday's misses surfaced first** with a red marker («دیروز اشتباه») — closure on
  yesterday's failures.
- **The week strip** at the bottom: completed days ticked, today empty. The plan is visible,
  progress through it is visible, nothing else competes for attention.

Below the main card, collapsed and quiet: plan settings, progress link. **No feed, no
leaderboards, no social** — those are distraction machines for this audience.

### 9.2 Study plan (برنامهٔ مطالعه)

On first login (and editable later), a 2-minute setup wizard:

1. **Target exam** — کنکور year (or school finals), optional exam date.
2. **Books in scope** — default: all math books of the student's grade track, checkable list
   (from books_catalog.json). e.g. «حسابان ۲ ✓، هندسه ۳ ✓، گسسته ✗».
3. **Daily capacity** — 10 / 20 / 40 questions per day (default 20; can edit anytime).
4. Optional: «فقط این فصل‌ها برای ۲ هفته آینده» — a short-term focus override
   (e.g. exam next week on chapters 1–2: queue draws only from those).

The plan drives the queue builder (§5.2): "new concepts" come only from in-scope books in
curriculum order; review concepts are naturally the ones previously attempted. If the student
has an external مدرسه/کنکور institute plan, they can pin chapters manually — the app obeys.

### 9.5 Other screens (quiet, secondary)

1. **برنامه و پیشرفت (Plan & Progress)** — one screen, two tabs:
   - *Plan:* books in scope with checkboxes, daily capacity, exam date.
   - *Progress:* curriculum tree (books → chapters → lessons) with mastery bars
     (نیاموخته / درحال‌یادگیری / یادگرفته / مسلط), drill-down to concepts with per-concept
     stats and a "مرور این مفهوم" button (adds an extra slot today).
2. **تقویم (History)** — a month grid with per-day counts and accuracy; tap a day to see the
   questions answered that day. Purely a review surface, not a feed.
3. **تنظیمات (Settings)** — daily capacity, notification time, font size default, logout.

Navigation is a thin bottom bar with 3 items only: **امروز | پیشرفت | تنظیمات**. No other
top-level destinations exist. The app has exactly one primary action per screen.

### 9.6 Rendering pipeline

Markdown → `react-markdown` + `remark-math` → KaTeX (RTL-aware container). Figures served from
CDN. Font-size controls on question view (large-print mode) — this is why content is text, not
images.

### 9.7 Screens (admin)

1. **Content browser** — curriculum tree → concepts → questions; inline edit of md/options;
   upload figures; toggle reviewed.
2. **Generation console** — pick template, count, difficulty; watch worker queue; accept/reject
   generated questions.
3. **Stats dashboard** — per-question correct-rate, flagged questions, student cohorts.

## 10. Content Import Pipeline (bank → platform)

1. **Ingest PDFs** (the existing test sets): render pages → detect question blocks (horizontal
   rule detection, proven in pilot) → crop screenshots.
2. **LLM extraction pass** (vision): for each block → meta.json
   (stem, options, answer, topic/subtopic, figures list) + question.md. Confidence recorded.
3. **Curriculum mapping**: map each question's topic/subtopic to a `concept_id` via the
   curriculum tree; ambiguous ones → admin review queue.
4. **Template assignment**: LLM clusters questions of a concept into templates (pattern naming);
   admin validates clusters once per concept.
5. **Dedupe**: embedding similarity within concept > 0.9 → merge candidate list for admin.
6. **Import**: folders to storage + DB rows. Pilot (60 questions of grade 9) imports as-is as
   the first seeded concept set.

Throughput estimate: ~500–1000 questions/day of LLM extraction in batches; the full 10k bank
≈ 2–3 weeks of background runs (or faster with parallelism).

## 11. Product Rules & Edge Cases (decisions to confirm)

11.1 **Exact repeats**: allowed only when a concept's family has exactly 1 question AND
     generation is unavailable. UI shows "تکرار سؤال قبلی" honestly.
11.2 **Concept vs question mastery**: streaks/intervals track the *concept*, but a wrong answer
     on a never-seen variant counts like any wrong answer (no forgiveness).
11.3 **Grade change** (student moves ۹→۱۰): concept_states persist; new book's concepts start
     fresh; overlapping concepts (e.g. مجموعه‌ها) are matched by identical titles → carry state.
11.4 **Practice mode** (free chapter practice): responses recorded for stats/difficulty
     calibration, but do NOT modify concept_state intervals — only the daily queue does
     scheduling. (Alternative: practice also affects scheduling — decide.)
11.5 **Multi-concept questions** (e.g. a word problem needing both fraction arithmetic and
     LCM): primary concept = the tested skill; secondary concepts listed; response updates only
     the primary. Secondary usage counted for analytics.
11.6 **Tashrihi grading**: phase 1 = self-grade (show solution, student taps درست/نادرست);
     phase 2 = AI grading of typed/photoed answer (separate feature, later milestone).
11.7 **Cheating/answer exposure**: correct answer never sent to client before submission;
     solution only after answering; options shuffled per student (server stores real index).
11.8 **Offline/low bandwidth**: figures are PNG ≤ 200KB; pages ≤ 150KB JS; PWA later.

## 12. Non-Functional Requirements

- **Latency:** question fetch < 300ms p95 (cache hot questions); queue generation < 2s.
- **Scale target:** 10k questions, 100k students, 10M responses/year — single PostgreSQL
  instance is fine at this scale with the given indexes.
- **Availability:** stateless API (2+ replicas), managed Postgres with PITR.
- **Security:** OTP rate-limiting, JWT rotation, admin role checks on every mutating endpoint,
  per-student rate limit on generation-triggering endpoints.
- **Backups:** nightly dump + WAL archiving; the question content folders are in object storage
  with versioning.
- **Privacy:** minimal PII (phone, name); responses pseudonymized for analytics.
